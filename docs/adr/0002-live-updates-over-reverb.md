# 2. Live updates are signals over Reverb, not polls

Date: 2026-09-24

## Status

Accepted

## Context

Seven Livewire components polled: the three sidebar blocks on every page,
every 3 to 60 seconds, and four "waiting for…" banners every 3 seconds. Each
tick asked the database whether anything had changed, whether it had or not,
and the sidebar never saw work started from the command line or the scheduler
until its next tick. The app runs on a LAN, often on small hardware, and has no
TLS certificate.

## Decision

Pages wait for a **signal** from Laravel Reverb instead of asking on a timer.

- **Signals, not state.** Two events: `SystemUpdated` on the private `system`
  channel (`what`: activity, quota, storage) and `GameUpdated` on
  `games.{id}` (`what`: hashed, identified, artwork, rating, failed). A
  component that hears one runs the same read or check its poll used to, so
  there is one way for it to get its figures.
- **Sent now, never queued** (`ShouldBroadcastNow`, through
  `App\Support\LiveUpdates`). A queued signal would wait behind the scans and
  downloads it reports on. A failed send is logged once a minute and
  swallowed: a signal may never fail the work that sent it.
- **Queue activity comes from one listener on the queue itself**, which hears
  jobs from the interface, the command line and the schedule alike.
- **Reverb runs inside the web container**, on 127.0.0.1:8080, in a restart
  loop. nginx proxies only `^~ /app/` (the websocket) to it; the publishing
  API under `/apps/` is not reachable from the network. Plain http end to end;
  the browser connects to the page's own host and port and picks `ws` or
  `wss` from the page's protocol, so a TLS proxy in front would still work.
- **Keys are generated by the entrypoint** when `.env` does not set them, once,
  into `storage/framework/reverb.json`, which the config reads. A file rather
  than only an exported variable, so `docker exec … php artisan` sees them too;
  kept across restarts, so an open tab reconnects with the key it loaded. The
  browser reads the key from a `<meta>` tag. Nothing is baked into the image or
  the JS bundle.
- **The browser folds a burst** of signals into at most one re-render a second,
  always running the last, and every listener runs once more when the socket
  reconnects after a drop.
- **No fallback polling, with one exception.** The disk figure keeps a
  five-minute poll: its used half moves as games are identified, which sends no
  system signal, and reading it is a single query (no page reads the disk; see
  MeasureLibrary). Wait banners have no poll either; a one-shot
  timer runs their existing check once at the timeout, so a job that hangs
  without failing still ends its banner.

## Considered options

- **Keep polling.** Simple and already working, but it costs a request per open
  tab per tick for figures that rarely change, and misses out-of-band work.
- **Put the new state in the event.** Saves one request per signal, but gives
  every component two ways to get its data that can disagree.
- **Queued broadcasts on their own queue.** Needs another worker, and adds
  latency for nothing on a single machine.
- **Expose Reverb's port directly.** An extra port to publish and firewall, and
  it exposes the publishing API.

## Consequences

- A page shows nothing live if Reverb is down; the app itself keeps working.
- Adding something new to wait on is a new `what` value, not a new event.
- Development runs Reverb too, with `--debug`, so the same path is exercised.
